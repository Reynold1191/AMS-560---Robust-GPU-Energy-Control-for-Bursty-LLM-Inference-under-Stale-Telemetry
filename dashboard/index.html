Does knowing how old your telemetry is make GPU energy control safer?

A controller picks the GPU clock every second to save energy while keeping LLM request latency under an SLO. It only sees telemetry that is d ms old. We compare a reactive controller (naive) against one that knows the telemetry age, forecasts over it and ignores lagging latency signals (robust), on a real RTX 5060 Laptop GPU.

Experiment setup

How one run works

  1. Load generator sends Poisson requests: steady, ramp or a 4× sharp burst.
  2. LLM worker serves them in batches of 16 (Qwen2.5-0.5B, long-context prompts).
  3. Telemetry (power, clock, queue, P95, error-budget burn, arrival rate) goes through a DelayBuffer, so the controller sees data that is d ms old.
  4. Controller picks one of 5 clocks (180 to 2122 MHz) every 1 s. nvidia-smi locks it.
  5. Metrics integrate NVML power into joules and record every request's latency against the 5 s SLO.

How to read it

  • Arrival rate: the solid line is the true 10 s rate. The dotted line is what the controller saw (delayed).
  • Queue: solid is true, dotted is observed. At 2500 ms delay the controller sees a queue that is 2.5 s old.
  • Clock: the clock each controller chose. Naive often stays at 2122 MHz after the burst because the 60 s P95 window still remembers it. Robust drops back when there is no backlog.
  • Latency: one dot per request, plotted at its arrival time. Points above the red SLO line are misses.

Probe and calibration

180 MHz cannot keep up (P95 of about 128 s), so it is only a fallback clock. 667 MHz has the lowest J/token but misses the SLO in a burst. That is the trade-off a controller has to manage.
